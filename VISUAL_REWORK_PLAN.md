# Визуальная переработка LANCER // РЕЕСТР — для удобства пользователя

## Контекст

Сайт — статический vanilla HTML/CSS/JS конструктор персонажа/меха для Lancer
(`index.html`, ~3300 строк, без фреймворка и сборки). У него уже есть
осознанная sci-fi HUD эстетика с токенами (`:root` CSS-переменные), тремя
шрифтами и заметной визуальной идентичностью — это не редизайн бренда, а
переработка **для удобства использования**: доступность, отзывчивость на
разных экранах, устранение накопившейся непоследовательности разметки.

Разведка кода (см. критичные файлы ниже) выявила конкретные, подтверждённые
проблемы:
1. **Ноль accessibility**: нет `aria-*`/`role=` нигде; вкладки — обычные
   `<button>` без `aria-selected`/`role="tablist"`; тултипы работают только
   на hover (недоступны с клавиатуры/тача); в модалках нет `Escape`,
   focus-trap или возврата фокуса (подтверждено через grep — совпадений
   `Escape|keydown` не найдено).
2. **Только 4 media-запроса** (1020px, 560px, 760px, print) — провал в
   диапазоне 560–1020px и <480px, риск переполнения текста при длинных
   русских подписях с фиксированными px-размерами шрифта.
3. **Дублирование компонентов**: `.stat`/`.statrow`/`.pgstat` — три похожих,
   но разных по разметке тайла для одного и того же типа данных (HP/Броня/
   Уклонение), сам код это признаёт в комментариях (строки 414-416, 420-421).
4. **162 инлайн `style="..."` атрибута** в JS-шаблонах рендера — смесь
   реально динамических значений (цвет из данных, `width:${pct}%`) и
   статичных одноразовых хаков, которые стоило бы вынести в классы.
5. Интерактивные элементы (`.stepbtn` 34px, `.xbtn` 32px, `.stattip` 16px)
   меньше рекомендованного минимума touch-target 44×44px.

Задача согласована с пользователем как best-effort accessibility (без
формального WCAG AA аудита каждой пары цветов), полный охват из 5 фаз
(включая рискованную консолидацию компонентов), aria-тексты на русском.

Используемые ориентиры — уже установленные в `.claude/skills/` дизайн-скиллы:
- **design-system** — модель токенов (Primitive → Semantic → Component) и
  Component Spec Pattern — применяется в Фазе 3 для объединения тайлов.
- **ui-ux-pro-max** — точечные проверяемые правила: touch-target 44×44px,
  transition 150–300ms на `transform`/`opacity`, семантические цветовые
  токены вместо сырого hex, z-index-шкала.
- **web-design-guidelines** — ревью-скилл (тянет живые гайдлайны с
  vercel-labs/web-interface-guidelines через WebFetch) — используется в
  конце как проверка диффа, а не как исходные правила.

**Жёсткие ограничения**: не трогать `frame.name`/`frame.variant` (ключи
лицензионной логики), не трогать i18n-оверлей (`localizeData`,
`loadBaseData` и т.д.), не ломать существующую HUD-эстетику (шрифты, цвета,
угловые скобки карточек, grid-фон). Тестов нет — верификация только вручную
в браузере (`python3 -m http.server`).

## Фаза 0 — База для сравнения (без изменений кода)

Пройтись по всем 9 вкладкам (ПИЛОТ, НАВЫКИ, ТАЛАНТЫ, МЕХ-НАВЫКИ, ЛИЦЕНЗИИ,
ШАССИ, ВООРУЖЕНИЕ, CORE, ИТОГ) на ширинах экрана ~1400px, 1020px, 768px,
400px и сделать скриншоты — единственный доступный способ регрессионной
проверки в отсутствие тестов. Работать в отдельной ветке.

## Фаза 1 — Accessibility (наибольшая ценность, минимальный риск)

Затрагивает: `renderTabBar()`, `renderTab()`, `wireStatTooltips()`,
`statIconHTML()`, `modal()`/`closeModal()`, CSS около 333 (`:focus-visible`),
461-471 (`.tab`).

1. **Вкладки → настоящий ARIA tablist**: контейнеру `#tabs` — `role="tablist"`;
   каждой кнопке в `renderTabBar()` — `role="tab"`, `aria-selected`,
   `aria-controls="tab-panel"`, roving `tabindex`; контейнеру `#tab` —
   `role="tabpanel"`, `aria-labelledby`. Добавить навигацию стрелками
   (Left/Right/Home/End) рядом с существующим `.onclick`.
   **Проверка**: Tab заходит на активную вкладку, стрелки переключают и
   активируют, `aria-selected` совпадает с классом `.active`.
2. **Глобальный `:focus-visible`**: одно правило рядом с `::selection` (334)
   — видимое кольцо фокуса на всех интерактивных элементах без изменения
   вида при клике мышью.
   **Проверка**: Tab по вкладке ВООРУЖЕНИЕ (много `.item`/`.chip`) — кольцо
   видно на каждом фокусируемом элементе.
3. **Тултипы доступны с клавиатуры**: `.stattip` получает `tabindex="0"`,
   `role="button"`, `aria-label` (на русском); `wireStatTooltips()`
   дополняется `focus`/`blur` и `Escape`.
   **Проверка**: Tab до иконки статы в HUD — тултип показывается по фокусу,
   Escape скрывает.
4. **Модалки: Escape + focus trap + возврат фокуса**: `keydown`-слушатель на
   `Escape` → `closeModal()`; при открытии — сохранить `activeElement` и
   перевести фокус в панель; Tab не должен выходить за пределы модалки;
   при закрытии — вернуть фокус на кнопку-триггер.
   **Проверка**: открыть редактор кастомного навыка, потаббировать (фокус не
   уходит наружу), Escape закрывает и возвращает фокус.
5. **Точечная правка контраста**: измерить `--faint` (#54637a) на фоне
   `--bg-grid`/`--panel`; если контраст низкий для мелкого текста —
   поднять яркость токена на уровне `:root` (каскадируется само, без правок
   по местам использования). `--accent`/`--amber`/`--red` не трогать.
   **Проверка**: визуально — `--faint` всё ещё читается как приглушённый
   вторичный текст, не сливается с фоном.
6. Блочный rewrite `label for=` не нужен — существующий паттерн
   `<label>`-обёртки уже семантически корректен; точечно проверить только
   нестандартные случаи (если где-то есть чекбоксы/радио вне этого паттерна).

## Фаза 2 — Отзывчивость / брейкпоинты

Затрагивает: 368/373 (1020px), новые `@media` около 640-680px и <480px,
`.brand .name` (354), `.frame-thumb` (516-518), `.statgrid`/`.pgstats`/
`.action-stats`.

1. Добавить средний tablet-брейкпоинт (`max-width:680px`): `.statgrid` с
   `repeat(3,1fr)` на `repeat(2,1fr)`, чтобы длинные подписи вроде
   "ТЕХ-АТАКА" не обрезались; уменьшить min-width `.pgstats`, gap
   `.action-stats`.
2. Добавить брейкпоинт для маленьких экранов (`max-width:480px`):
   `.brand .name` с фиксированных 21px на `clamp(17px,5vw,21px)`; проверить
   `.item .nm` на перенос в 2 строки; проверить `.modal .panel` на этой
   ширине (сейчас `min(880px,94vw)`).
3. Точечно перевести на `clamp()` только те фикс-px значения, что реально
   рискуют переполнением текста (длинные кириллические подписи рядом с
   числовыми полями типа `.stepval`, `.llpick .num`) — декоративные/иконки
   (миниатюры, угловые скобки) не трогать.
   **Проверка**: ресайз браузера на 1024/768/600/400px, особое внимание
   вкладкам ШАССИ (миниатюры + statgrid) и ВООРУЖЕНИЕ (крепления +
   action-stats).

## Фаза 3 — Консолидация компонентов (риск-фаза)

Затрагивает: 407-442 (CSS `.stat`/`.statrow`/`.pgstat`), их точки вызова
(`renderHUD()` 1436-1445, детали шасси, снаряжение пилота), повторяющиеся
статичные inline-`style=` (1443, 1527, 1531, 1533, 1536, 1542-1543 и
аналогичные).

1. По модели design-system-скилла (Component Spec Pattern) спроектировать
   единый `.stattile` с модификаторами (`--compact`, `--row`, `--icon-only`),
   заменяющий `.stat`/`.stat.compact`/`.statrow`/`.pgstat`. Мигрировать
   **по одному месту использования за раз**: сначала HUD-statgrid (всегда
   виден, проще всего), затем `.statrow` (детали шасси), затем `.pgstat`
   (снаряжение пилота) — на каждом шаге визуальная проверка. Старые CSS-
   правила удалять только после `grep` подтверждения отсутствия оставшихся
   вызовов класса.
2. Инлайн-стили: вынести в utility-классы только повторяющиеся статичные
   паттерны (например, `.mt-sm`/`.mt-md` для отступов, `.heading-sub` для
   повторяющегося блока `font-family:'Chakra Petch';font-size:17.5px;
   margin:28px 0 6px` на 1542 и похожих местах). Динамические инлайны
   (`style="color:${srcColor(...)}"` на 1472, `style="width:${pct}%"` в
   `bar()`) не трогать — значение вычисляется на рендере, инлайн там
   правильный выбор.
   **Проверка**: подсчёт `grep -c 'style="'` до/после должен заметно упасть
   за счёт статичных случаев; HUD, деталь шасси и тайлы брони пилота
   выглядят идентично (или аккуратнее) по сравнению со скриншотами Фазы 0.

## Фаза 4 — Полировка взаимодействия

Затрагивает: `.stepbtn` (563), `.xbtn` (628), `.stattip` (449), `.chip`
(635), transition-длительности, z-index.

1. **Touch-таргеты**: увеличить `.stepbtn`/`.xbtn` до 44px (либо визуальный
   размер сохранить, а хитбокс расширить через `min-width`/`min-height` +
   `display:grid;place-items:center`, если 44px визуально громоздко рядом с
   плотным HUD — решать по месту). `.stattip` (16px, декоративная иконка) —
   после Фазы 1 уже доступна с клавиатуры, расширение хитбокса — низкий
   приоритет.
2. **Аудит transition**: текущие `.15s`/`.25s` в основном уже соответствуют
   правилу 150-300ms на `transform`/`opacity`; `.brow .bar i{transition:
   width .25s}` (403) — анимация `width`, не в списке рекомендуемых
   свойств, но это тонкая полоска прогресса и она уже работает — оставить
   как есть, не рисковать ради формальной чистоты.
3. **z-index**: задокументировать текущую фактическую шкалу
   (`#boot:200`, `.topbar:60`, `.modal:120`, `.stattip-box:1000`) одним
   комментарием у `:root` (297), не перенумеровывать — риск сломать
   стекинг ради отсутствия функциональной пользы.
   **Проверка**: точность клика по степперам +/- на вкладках Навыки/
   Таланты/Мех-навыки в devtools mobile emulation.

## Фаза 5 — Финальная проверка

1. Прогнать скилл `web-design-guidelines` (ревью-режим через WebFetch) на
   финальном диффе `index.html`.
2. Полный клик-проход по всем 9 вкладкам на 4 ширинах экрана, сравнение со
   скриншотами Фазы 0.
3. Убедиться, что `frame.name`/`frame.variant`-логика и i18n-оверлей не
   затронуты: `git diff` не должен касаться `derived()`, функций поиска
   лицензионного ключа или кода загрузки/оверлея данных (`loadBaseData`,
   `localizeData`, `fetchJSON` и т.д.) — изменения только в разметке/CSS/
   рендер-функциях и новых JS-обработчиках взаимодействия.

## Порядок фаз — обоснование

Фаза 1 первая — она аддитивна (новые атрибуты/слушатели), почти не рискует
что-то визуально сломать, и ценна сама по себе. Фаза 2 — чисто CSS,
изолирована в media-запросах, легко проверяется ресайзом. Фаза 3 —
наибольший риск регрессии (много точек вызова), поэтому идёт последней из
содержательных фаз — если время поджмёт, самая ценная и безопасная работа
уже сделана. Фаза 4 — низкорисковая полировка, логично идёт после
консолидации, так как трогает частично те же классы кнопок.
