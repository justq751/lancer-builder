# План: перенос перевода lancer-builder в Foundry VTT 13

Дата исследования: 13 ноября 2026. Статус: реализован и локально установлен модуль 0.1.1; игровые проверки выполняет пользователь.

## Ход реализации

- Созданы `tools/export_foundry_locale.py`, модуль в `foundry/lancer-ru-content/`, команды сборки/проверки, тесты, инструкция и ZIP в `foundry/releases/`.
- Экспортируются 613 записей, включая теги; 193 поля адаптированы к структуре Foundry. Отчёт `coverage.json` перечисляет 12 неперенесённых полей и границы поддержки, включая отдельные действия/развёртываемые объекты.
- Сборка проверяет синхронность upstream, нормализованных данных и локалей, обнаруживает дубликаты и stale, сохраняет UUID и параметры.
- Локальные проверки: 4 Python-теста экспортера, 10 Node-тестов адаптера и UI, 54 существующих unit-теста сайта; JSON валиден.
- Пользователь включил модуль в Foundry 13.351 + LANCER 3.1.3 и подтвердил частичный перевод реального листа Балора. По диагностике исправлены начальный индекс без LID, сериализация `<br/>`, регистр REPAIRS и отсутствующие ключи характеристик в верхнем регистре.
- С момента просьбы пользователя агент не управляет браузером Foundry. Повторная визуальная проверка версии 0.1.1, drag-and-drop, лицензии, чат, теги и смена языка остаются за пользователем.
- Старые предметы персонажей не мигрируются. Поля неподдерживаемых категорий и неоднозначные тексты не подменяются. Публичная публикация не выполнялась.

Ниже сохранён исходный план; его игровые пункты нельзя считать выполненными только на основании unit-тестов.

## Вывод

Перевод можно переиспользовать. Основной ключ соответствия — ID из `locales/ru/*.json` → `system.lid` документа Foundry, с учётом типа документа и исключений. Переносить нужно исходные пары `{en, ru}`, а не готовый локализованный объект сайта: схема Foundry отличается, некоторые тексты находятся внутри профилей, часть данных вообще не является Item.

Предлагаемый результат — отдельный модуль `lancer-ru-content`, использующий существующие Babele и lib-wrapper. `ru-ru` продолжает переводить Foundry и интерфейс системы, `lancer-ru-ui-patch` — дополнять интерфейс. Новый модуль в первую очередь переводит игровой контент; самостоятельную полную замену этих двух модулей пока не делать.

Реализуемость сопоставления подтверждена по установленным файлам. Работоспособность Babele с создаваемыми LANCER справочниками мира и переносом на листы должна быть подтверждена отдельной проверкой до массовой реализации.

### Объём и совпадение ID

`python tools/locale_coverage.py` сообщил **3248/3248 переведённых пар**, без сообщений о stale и generator drift. Это заполненность словаря сайта, а не доказательство полного перевода всей системы Foundry.

Сопоставлены ключи локалей со встроенными английскими наборами установленной системы: core и всеми восемью дополнениями. Для статусов учтён алгоритм получения LID из `unpackStatus`.

| Категория | Записей в локали | Найдено соответствий ID |
|---|---:|---:|
| frames | 55 | 55 |
| weapons | 123 | 123 |
| systems | 186 | 186 |
| mods | 11 | 11 |
| talents | 40 | 40 |
| skills | 22 | 22 |
| core_bonuses | 32 | 32 |
| pilot_gear | 61 | 61 |
| statuses | 16 | 15 |

Единственное несовпадение в этой проверке — `shut-down`: встроенный `unpackStatus` при отсутствии `id` удаляет дефис из `icon`, получая `shutdown`. Нужен явный alias `shut-down` → `shutdown`, а не общее удаление дефисов из любых ID. Отдельно проверить путь внешнего LCP: парсер может задавать статусам ID иначе.

Проверка выше устанавливает наличие ID, но ещё не равенство английских текстов, уникальность ID между пакетами или наличие этих документов в конкретном мире.

### Роль установленных модулей

- `ru-ru` подключает `i18n/systems/lancer.json`: интерфейсные ключи `TYPES.*`, `lancer.*`. В установленном коде нет отдельного обработчика Babele для LANCER и не найдено каталога перевода его справочников.
- `lancer-ru-ui-patch` содержит только `languages` → `lang/ru.json`; его README прямо ограничивает назначение интерфейсом.
- Babele 2.9.1 предоставляет `babele.init`, регистрацию источников, mappings, converters и identity extractors. Стандартное сопоставление использует `_id`, `name`, `sourceId`; `system.lid` автоматически не участвует. Для LANCER нужен зарегистрированный extractor и соответствующий mapping.
- В `system.json` LANCER только два статических compendium: макросы и журнал. Игровые Items создаёт LCP Manager в справочниках **мира**, в частности `world.mech-items`, `world.pilot-items`, `world.status-items`; развёртываемые Actor — `world.player-actors`. Содержимое нескольких LCP группируется по типам, а не по отдельному справочнику на книгу.

## Карта переноса

Во всех Item-категориях `name` переводится в имя документа, ID остаются прежними. Ниже перечислены поля-кандидаты; окончательный allowlist сверить с фактическими экспортами документов 3.1.3.

| Источник | Тип / место Foundry | Преобразование |
|---|---|---|
| frames | Item `frame` | `description` → `system.description`; traits → `system.traits`; core_system → `system.core_system`, включая названия, эффекты и действия |
| weapons | Item `mech_weapon` | Эффекты `effect/on_hit/on_attack/on_crit` → поля `system.profiles[]`; оружие без profiles получает один профиль при импорте; вложенные actions сохраняют механику |
| systems | Item `mech_system` | `effect/description` → одноимённые поля `system` |
| mods | Item `weapon_mod` | `effect/description` → `system`; `on_hit/on_attack/on_crit` нельзя автоматически считать поддержанными: unpacker 3.1.3 их не переносит в одноимённые поля |
| talents | Item `talent` | `description/terse`, `ranks[].name/description` → поля `system`; ранги не заменять целиком |
| skills | Item `skill` | `description/detail` → `system` |
| core_bonuses | Item `core_bonus` | `effect/mounted_effect` → `system` |
| pilot_gear | Item `pilot_armor`, `pilot_weapon`, `pilot_gear` | Разделить по исходному type Armor/Weapon/Gear; description/effect переносить только в поддерживаемые поля |
| statuses | Item `status`, отображение состояний и ActiveEffect | `terse/effects` → `system`; учитывать склейку массива effects в HTML и alias shutdown; отдельно проверить имена/описания ActiveEffect, не меняя changes |
| tags | Настройка системы и класс `Tag` | Не Item: определения хранятся в `setting_tag_config`; на предметах только `{lid, val}`. Нужен отдельный адаптер отображаемых name/description |
| actions | Интерфейс и вложенные действия | Отдельный Item action не объявлен. Определить источники встроенных действий и переводить через существующие UI-ключи либо конкретные вложенные поля |
| enums, stat_labels | Интерфейсные словари Foundry | Использовать как терминологический источник; ключи сайта не совпадают с ключами системы |
| glossary, manufacturers | Справочные/конфигурационные данные | Нет прямого универсального Item-соответствия; использовать только там, где найден конкретный отображаемый текст |
| backgrounds | Поле биографии пилота | Нет отдельного Item background. Словарь сайта нельзя автоматически накладывать на произвольный пользовательский текст |
| ui | Интерфейс сайта | Не загружать целиком в Foundry. При необходимости брать отдельные формулировки с явным сопоставлением ключей |

Для traits, ranks, profiles, actions сначала искать точное исходное имя в пределах родительского ID; при наличии стабильного LID предпочитать его. Сохранять исходную идентичность до перевода, чтобы повторное применение не зависело от уже русского имени. Не сопоставлять вложенные элементы только по индексу и не использовать нечёткое совпадение.

## Какие места затронет реализация

| Место | Планируемое изменение |
|---|---|
| `locales/ru/*.json`, `data/*` | Только входные данные; точечные правки перевода при подтверждённых ошибках |
| `tools/export_foundry_locale.py` | Экспорт, проверка соответствий, отчёт |
| `foundry/lancer-ru-content/` | Манифест, адаптер и генерируемые словари |
| `tests/` | Малые фикстуры и проверки экспортера/адаптера |
| `package.json` / CI | Команда проверок новых файлов при необходимости; существующий `test:json` может не охватывать новый каталог |
| `.assetsignore` | Исключить новый каталог `foundry` из публикации сайта; Pages использует allowlist, его проверить |
| `README.md` | Команды сборки и ссылка на инструкцию модуля |
| `tests/golden/L.*.json` | Обновлять только при намеренных правках локалей, влияющих на сайт |

Ни runtime сайта, ни установленные папки Foundry не требуется менять для разработки экспортера. Копирование готового модуля в Foundry и любые операции с миром — последующий этап реализации.

## Критерии готовности

1. Модуль устанавливается и включается на Foundry 13 + LANCER 3.1.3 с указанными зависимостями.
2. Поддерживаемые документы сопоставляются по LID без зависимости от случайных Foundry `_id` и переведённых имён.
3. Переведены поддержанные поля core и восьми дополнений; каждый неперенесённый текст отражён в отчёте с причиной.
4. Расчёты, атаки, профили, лицензии и ссылки работают; применение переводов не меняет игровые значения.
5. Перевод обновляется из `locales/ru` одной командой, без ручного редактирования сгенерированного словаря.
6. Документация различает перевод справочников, новых импортированных Items, старых документов мира и оставшихся категорий без перевода.

## Справочные источники

- [Foundry: Languages and Localization](https://foundryvtt.com/article/localization/) — языковые файлы и объединение словарей интерфейса.
- [Foundry 13: Localization API](https://foundryvtt.com/api/v13/classes/foundry.helpers.Localization.html) — интерфейс локализации.
- [Репозиторий Babele](https://gitlab.com/riccisi/foundryvtt-babele) — проект зависимости; конкретные возможности выше проверены по установленному коду 2.9.1, а не по обещанию совместимости другой версии.

Не проверены: запущенный Foundry, активный мир, реальные документы после импорта и поведение Babele в игре. Эти проверки намеренно стоят первыми в реализации; сейчас выполнен только анализ файлов и словарей.
